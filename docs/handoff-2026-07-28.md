## Current production architecture

- The public production query mode is graph-free `srht-pq-scan` with bounded
  global IVF routing, paged product-code scans, and lossless exact reranking.
  Graph and mixed graph/scan modes remain research controls.
- The automatic production storage default is all-Parquet for normal segment
  and WAL tables. The independently reproduced normal-segment and 220-case WAL
  qualifications rejected Vortex as the automatic default. Vortex remains an
  explicit experimental backend, not an adaptive row-count choice.
- Exact dense vectors are independently range-addressable in standard Arrow
  IPC sidecars and fixed-width global pages. Small atomic heads, pointers,
  transaction state, commit markers, and coordination records use checked
  packed binary codecs.
- Ingest uses immutable WAL runs sharded by logical cell and lane. One
  transaction commit marker atomically publishes a multi-cell append. Explicit
  IDs do not pass through a collection-wide generated-ID CAS; fixed claim
  shards and fenced transaction state coordinate duplicates and recovery.
- Build and serving have bounded process-wide CPU, I/O, query, cell-decode,
  code-read, and exact-rerank admission. The default is four admitted searches
  and twenty-four cell reads/decodes, with separately bounded CPU and I/O
  pools.
- No released compatibility contract exists. Prefer coherent breaking changes
  and reject old experimental formats clearly instead of keeping migrations or
  duplicate write paths.

The authoritative detail is in `docs/architecture.md`,
`docs/storage-format.md`, and `docs/research/release-readiness-2026-07-26.md`.

## Stabilized feature surface

The end-to-end lifecycle matrix covers WAL visibility, typed query
canonicalization, exact/approximate ordering, flush, reopen, upsert, delete,
compaction, garbage collection, and final reopen for:

- primary and named dense vectors: float32, float16, bfloat16, E4M3FN, E5M2,
  and int8;
- primary and named packed binary vectors with Hamming and Jaccard;
- primary and named sparse vectors using float32 and float16;
- BM25 text, all non-empty dense/sparse/BM25 hybrid signal combinations;
- late interaction using float32 and float16; and
- UTF-8 and opaque binary record IDs.

SIMD correctness is covered for dense metrics, float16/bfloat16/int8/FP8
decode, packed binary scoring, sparse and lexical scoring, late-interaction
MaxSim, routing, PQ, SRHT/FWHT, and Fast-TurboQuant arithmetic. Float32 uses
native vector arithmetic. Lower-precision formats decode in bounded blocks and
then use the shared float32 SIMD kernels. Irregular gathers/scatters and packed
code lookups remain scalar where portable SIMD cannot improve them safely.
Wasserstein and dynamic time warping remain scalar dependency chains.

Correctness is established, but publication-grade end-to-end SIMD speedups
across every datatype are not yet established. The local Apple Silicon kernel
micro-gate measured float16 conversion at 1.23x and blocked E4M3FN decode at
5.21x versus their scalar controls; those are diagnostics, not product claims.

## Evidence and claims policy

- Product-comparison numbers may come only from first-party commercial
  documentation, primary papers, or a successfully audited direct paired run.
- External reported numbers are context-only and never merged into the direct
  sample series.
- “Lower latency at matched recall” is permitted only if the predeclared
  hierarchical bootstrap accepts both the p95 ratio and recall-difference
  criteria. Otherwise report `no-superiority-claim`.
- Amazon S3 Vectors and BORSUK share the same measured client. Managed-service
  compute is undisclosed, so never claim BORSUK used weaker hardware.
- The failed v7 run supports no superiority statement.
