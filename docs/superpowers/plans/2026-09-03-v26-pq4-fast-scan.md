# V26 PQ4 Fast-Scan Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build and falsify a 128-bit PQ4 global candidate scan that can meet unchanged 99.5% oracle-attainment and 15-ms serving gates.

**Architecture:** Encode 32 three-dimensional, four-bit subquantizer codes into 32-row transposed Arrow blocks. Score them with AArch64 NEON table lookups into a reusable `u16` buffer, select bounded top-K rows by histogram, exactly rerank Arrow vectors, and reduce them to ten pages.

**Tech Stack:** Rust 2024, AArch64 NEON intrinsics, Rayon, Apache Arrow IPC, Parquet, SHA-256, Python unittest, AWS EC2 Spot/S3/SSM.

**Spec:** `docs/superpowers/specs/2026-09-03-v26-pq4-fast-scan-design.md`

## Global Constraints

- Use exactly 32 subquantizers, three dimensions each, 16 centroids, 32-row blocks, and 16 encoded bytes per row.
- Persist new strict Arrow artifacts only; do not add a PQ16 compatibility reader or aliases.
- The exact 100-million-row resident projection is 2,336,975,744 bytes.
- Scientific scoring accepts only backend `aarch64-neon-table`; scalar is test-only evidence.
- Candidate depths are exactly `[512, 1024, 2048, 4096]`; select exactly ten pages.
- Quality gates remain 975,000/800,000/995,000 ppm and maximum latency remains 15,000,000 ns.
- Development uses burned queries 0..31; sealed holdout is queries 32..511 and is opened once after the arm freezes.
- All evidence samples use Parquet; all receipts/results use canonical newline JSON.
- No query, truth, or page-body access is allowed during training or encoding; diagnostic page-body reads equal zero.
- Scientific execution uses the `causality` profile, Spot capacity in any eu-central-1 zone, SSM, pressure stops, and immediate termination.
