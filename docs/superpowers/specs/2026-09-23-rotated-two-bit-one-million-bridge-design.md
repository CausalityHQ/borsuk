# Rotated two-bit codes: one ReLAION-1M locality and serving bridge

## Decision and limits

The terminal-closed ReLAION-100k scalar-code cell at source `8d920de52b6d1469b9af565faf8dbf3049ce0f00` passed its fixed quality thresholds on 1,000 development queries: 98.418% mean GT100, 91% p05 GT100, and 99.51% GT10 page containment. Its exact arm on identical grouped rows reached 98.515%/92%. The code wave was 32 actual GETs and at most 15,423,240 bytes per query. The independent validator agreed. Its sampled combined RSS was invalid because the process-group sampler missed the forked evaluator; source `80ddf40533aefd3c24b7d3ea4539887aa94f91bb` then replayed identical query evidence and closed with a 1,582,702,592-byte combined peak, a 1,738,354,688-byte conservative evaluator-plus-broker bound, zero swap and a terminated Spot instance. The full readback and terminal identity are recorded in `docs/research/algorithm-first-page-layout-ledger.md`. The prerequisite for launching this 1M bridge is satisfied.

This bridge answers one design question: can the fixed 200-byte rotated two-bit row representation find and score enough ReLAION-1M rows from a query-blind, source-only eight-page group layout within a 32-GET/16-MiB code wave, then serve adjacent final-page **ranges** within a separate 32-GET/16-MiB data wave? It neither freezes a production format nor claims competitor parity. The 1M query/truth cohort is the already-burned frozen development cohort. Do not use validation or holdout queries.

## Frozen inputs and the routing hypothesis

Reuse the six immutable ReLAION-1M inputs registered in the V98 preregistration of `docs/research/algorithm-first-page-layout-ledger.md`: source, development queries, exact GT100, V85 generation manifest, 900k-row base Arrow object, and 100k-row delta Arrow object. Add the generation-bound V85 router Arrow object, 2,363,962 bytes and SHA-256 `e7beee3da272e694ff69f15d4343ff7c18f7d0b9e3d33788baea1ee34a25bf8e`, to recover the base-trained SQ8 `low` and `step` vectors for final-page decoding. Reauthenticate all seven objects by encoded length and SHA-256 before use. Reuse the source-derived base/delta page order and page row IDs from the V85 generation, but create a new incompatible code-group format. Partition consecutive pages within each object role into groups of eight, with a shorter last group per role. Every group has at most 8 × 256 = 2,048 rows. Its payload stores the 100k-proven source-centered, seed-`20260923` two-bit records in that exact physical row order, plus count and boundary headers. Do not blend base and delta pages or read old experimental code formats.

The one routing hypothesis is a resident float16 **group centroid** for each of the roughly 910 groups. Train the global float32 mean and all group centroids only from the 1M source in source ordinal order, accumulating float64 batches, then round centroid coordinates once to little-endian float16. Score all group centroids by squared L2 to the float32 query, accumulating in float64, and take the nearest 32 groups with stable `(score, role, group ordinal)` ties. The group centroid is a selector only; rows in fetched groups use the already frozen reconstructed-distance two-bit score and the same source-ordinal tie rule as the 100k cell. The mandatory norm-corrected score is diagnostic only. Do not tune group width, centroid precision, rotation seed, or score formula on these queries.

Historical V98 closed evidence establishes the risk and the code-group ceiling. Among its 1,024 retained pages per query, first-32-distinct eight-page groups contain only 91.463% mean GT100 and 65% p05; a truth-aware selection of 32 such groups contains 98.381% mean GT100, 91% p05, and 98.9% GT10. Those numbers are an inference from the authenticated V98 page/truth records, not a measurement of this new centroid selector. They justify testing the selector and reject reusing first-32 group order as the 1M candidate plan. At 200 bytes per row, even 32 full eight-page groups occupy at most 13,108,352 bytes including 36-byte group headers, below the 16-MiB code cap. The final-page layout has a different constraint: a truth-aware **32 individual page** selector reaches only 85.971% mean GT100 and 61% p05. The V99 exact-source ranked-gap **32 range GET** arm reached 98.424% mean GT100 and 91% p05 under 16,777,200 data bytes. This bridge must coalesce adjacent final pages into bounded S3 ranges; a 32-page gate is scientifically impossible on the frozen V85 page layout.

## Source-only build and authenticated storage

Before building any one-million-row code plane, run a separate immutable **centroid-selector screen** using the exact source-only group definition above. Its builder parses the generation pages and streams source vectors to train only the float16 centroids and row-count manifest; it does not encode rows or fetch query/truth during construction. After sealing, the evaluator opens the 1,000 frozen development queries and GT100, ranks all group centroids once per query, and records selected-group GT10/GT100 containment, p05, selected group identities and projected 200-byte code-wave bytes. The independent reducer reconstructs the centroid bytes and every query plan from the authenticated source and generation pages. If the fixed selected-group quality or 32-GET/16-MiB projected code budget fails, classify `group-centroid-selector-killed` and stop; do not build the 200-MB code plane or launch the full serving cell. This is one preregistered selector, not a search over group sizes or centroid representations. A screen pass establishes only routing feasibility and authorizes the full cell below; it is not a memory, S3 code-read or native serving claim.

The builder downloads and authenticates the source, generation, base, delta and router objects before it can fetch queries or truth. Read the Arrow pages in manifest order to build the unique ID → `(role,page,row)` map, rejecting duplicate, missing, non-live and physical-order disagreement with the sealed page roster; global source order need not match physical page order. Stream the source parquet in batches no larger than 4,096, twice: first compute the global mean and group centroid sums, then encode each source row and place its 200-byte record at the sealed physical position on local scratch. Check each source ID exactly once and the complete page roster. Never hold the full 1M float32 source matrix in process memory. Write the final group object, resident centroid object and canonical source-only seal, binding the five source-side object identities, seeds, row IDs, page boundaries, group offsets, per-group SHA-256, per-page Arrow payload SHA-256 and the exact generation-bound SQ8 codec. Upload sealed objects with create-only S3 writes, read them back and authenticate before evaluation. Version the group and centroid schemas as new incompatible research formats.

The evaluator starts only after the source-only seal closes. It runs unprivileged in a network namespace; a narrow root Unix-socket broker performs no-retry S3 Range GETs only at sealed code-group coordinates or page-range coordinates derivable from the sealed manifest, checks every group SHA-256 and checks each returned page payload against its sealed SHA-256. The broker's separate code and data GET/byte totals must equal canonical per-query evidence. Use one evaluator process and one broker process, with no parallel scorer subprocesses; `unshare`, `timeout` and `/usr/bin/time` are the only wrappers. Phase RSS includes the broker and every evaluator descendant, with an enforceable sampled process-tree cap and a separate conservative bound from `/usr/bin/time` maximum evaluator RSS plus measured broker peak and 64 MiB wrapper allowance; swap must remain zero. Cap each construct/evaluate/validate phase below 3 GiB RSS. Use a Spot `c7i.8xlarge` by default; preregister interruption as noneligible, preserve its terminal, terminate immediately, and restart only at a fresh immutable attempt prefix.

## Paired scoring and final-page serving

For each of the 1,000 frozen development queries, read exactly the 32 selected code groups by S3 Range GET. Assert at most 32 successful code GETs and 16,777,216 bytes, with no retry or cache substitution. Score their rows in batches of at most 2,048. On precisely these candidates, also score exact source float32 vectors from bounded local authenticated scratch reads; this is a paired diagnostic, never a serving path. For primary, diagnostic and exact arms separately, rank the top 8,192 candidate rows by `(score,source ordinal)` and feed their physical pages in that order to V99's fixed ranked-gap planner. It greedily merges the cheapest same-object adjacent page gaps until the final plan fits at most 32 S3 ranges and 16,777,216 encoded bytes. The plan may include interior pages whose rows were never scored; they count toward fetched bytes and recall. This is the frozen V99 shortlist/planner method, not a tuned 1M page count. Record four distinct denominators on all 100 frozen neighbors for each of all 1,000 queries: truth in the selected groups, truth in exact-score planned ranges, truth in primary-code planned ranges, and ranked recall after actual SQ8 serving. The exact arm reveals whether group selection or row scoring is responsible for misses. Source-ordinal ties are stable across all arms. No phase may call V97's eager `load_screen_inputs` or hold a full float32 source matrix; independent replay also streams source and reads exact candidate scratch in bounded batches.

Only if the exact grouped arm meets all three quality gates, continue to actual final-page serving: fetch the primary-nominated V85 base/delta page ranges through S3 Range GET, authenticate every included page against its sealed SHA-256, boundary and Arrow schema, decode SQ8 with the generation-bound `low`/`step` using the native V85 fused float32 arithmetic, and rank only fetched live IDs using an explicit frozen-plan adapter to the native candidate merge/tie rule. The existing V85 executable loads all delta rows resident and must not be used unchanged: that would expose unselected candidates. Record per-query code and data-range GET counts, encoded bytes, wall latency, GT10 and GT100 recall, p05, failures and instance identity. Use a fresh client with no application cache; distinguish S3 request time from CPU time. The evaluator must never write S3. The independent validator reconstructs source mean, group centroids, codes, grouping and all 1,000 candidate/range/recall records without calling the producer scorer or planner, and joins frozen query/truth IDs exactly.

## Fixed decision rule

First reject as provenance/implementation failure for any identity, read, count, exact-arm replay or independent validation mismatch. If selected-group truth containment misses mean GT100 ≥97.5%, p05 GT100 ≥90%, or GT10 ≥96%, classify `group-centroid-selector-killed`; this falsifies the fixed single-centroid selector, not every eight-page layout. If groups pass but exact-score planned **range** containment misses, classify `range-planner-killed`. If exact ranges pass but the primary two-bit ranges miss, classify `one-million-code-killed` and use the diagnostic only to locate estimator versus encoded-bit loss. If primary ranges pass but actual SQ8 serving misses the same recall gates, classify `final-page-serving-killed`. If all pass under both wave budgets and the combined memory gate, classify `one-million-quality-locality-advance` only. It still needs a separately measured two-generation 100M resident worksheet, concurrent generation and mutation proof, native serving latency/throughput cost under matched competitor workloads, API/recovery/package gates, and frozen 10M/100M campaigns before production readiness.

Do not inspect incomplete measurement files. Verify the terminal, controller exit, instance termination and every terminal-listed artifact by length/SHA-256 before making a decision. Preserve immutable 100k and V98 history under their original source identities; do not present cross-format numbers as one frozen comparison.
