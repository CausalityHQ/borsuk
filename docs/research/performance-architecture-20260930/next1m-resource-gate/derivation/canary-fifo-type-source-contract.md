## Why a second slice: a fail-open found when tracing "other types"
After cce5dabe the admission loop (path equality AND -p) is exact, but it only looks at entries that find reports as ! -type f ! -type d ! -type l. A SYMLINK (or regular file / directory) at the admitted path is therefore never examined by that loop. What stood between it and acceptance is the live-vs-copy digest. In cce5dabe lst() excluded the path for ANY non-file/non-dir type (! -path ./share/hook-hotplug-cmd) and the case-copy tar excludes the same name, so a symlink there was dropped from both sides, the digests were equal and C0 passed silently (the same weakness existed at the old path in d262). Regular file / directory: lst lists them (f/d branches are never excluded) while tar drops them, so the digests differ and C0 already refused.
Fix (one line, coordinator line 87): the lst() exclusion is now type-exact:  ex=(! \( -path ./share/hook-hotplug-cmd -type p \))  i.e. only a FIFO at that exact path is hidden from the live listing. A symlink (live or dangling) is now listed ("l ./share/hook-hotplug-cmd -> target"), the tar still omits it, the digests differ and C0 refuses ("copy of /run/cloud-init differs from the live tree"). The tar exclude stays a literal path (tar cannot test types); the digest comparison is the type enforcement. Admission loop, find, symlink guard, copy-special refusal: byte-identical to d262.
Resulting matrix at /run/cloud-init/share/hook-hotplug-cmd: FIFO accepted (loop pass, digests equal); socket and character/block device refused by the -p loop; symlink, dangling symlink, regular file, directory refused by the digest; foreign FIFO/socket anywhere else, the old root-level path, and the real FIFO next to any foreign special file refused by the loop.
