# BORSUK autoresearch program

## Goal
Ship the generic Rust S3/blob ANN library with correct mutation, publication,
generation-pinned reads, bounded resources, recovery and compaction/GC.
Optimize matched recall, tail latency, throughput and total lifecycle cost.
A fast screen is research evidence, never production readiness or a vendor win.

## Operating loop
1. Read the incumbent commit, completed evidence and append-only results.tsv.
   Keep one original handle per live job. Finish it; do not duplicate it.
2. Pick ONE causal hypothesis from measured loss/stage costs. Prefer an
   already admitted config knob before changing Rust. State prediction,
   editable files/knobs, protected metrics and a bounded falsifier.
3. Use ONE fresh contextless specialist for the complete separable slice:
   relevant code/base, factual requirements, constraints and acceptance only.
   Root retains experiment authority, reconciliation, integration and push.
   Do not split one hypothesis into many handoffs.
4. Freeze evaluator, corpus/ordering, requests/truth, config/binary/source,
   machine, cache/retry/load policy, time boundaries and resource envelope.
   Candidate agents cannot alter evaluator, truth, split or acceptance.
   Necessary format/evaluator changes are separate versioned changes with a
   new baseline; preserve immutable old artifacts, not compatibility code.
5. Reuse unchanged qualified machinery. Perform affected native checks for a
   code change; one assurance gate for the stable revision. All preparation,
   compilation and experiments run on bounded Causality EC2/EBS, not Devbox.
   Run authenticated real-input admission then a separate disposable canary.
6. Run the cheapest valid paired native screen, targeting <=600s measurement
   per trial where baseline timing permits. Compilation/setup are separately
   bounded and logged. Use fixed query membership/work, not truncation to
   reach a deadline. Compare both order pairs and record uncertainty.
7. After terminal status and strict seal/EOF validation, append a result row.
   Retain useful quality/latency/memory/cost Pareto candidates. A useful quality
   gain may exceed a prior efficiency target. Enforced resource rejection is
   not environment INVALID; neither proves an algorithm negative outside its
   envelope. A feasible larger envelope must be declared before retrying.
8. Promote one frozen finalist to repeated full-cohort confirmation. Keep
   looping autonomously within existing operational/spend authority.
   Do not ask for routine command approval. Do not weaken gates after results.

## Evaluation and acceptance
- Current lane: Cohere Wikipedia multilingual-v3, 1M, D1024, cosine k10.
  Keep library algorithms independent of these names/populations/splits.
- Current first32 flat/framed ABBA is fixed. It cannot establish population
  p95 or a 0.2 percentage-point recall difference (one hit is 0.3125pp).
- The historical1000 cohort is development/regression data, not a blind test.
  A new independently sealed query/truth holdout requires versioned admission:
  the current benchmark validator pins [100000,101000). Never silently relabel
  used data as untouched. Confirmation failures are recorded, not tuned away.
- Record paired recall/hit changes, underfill, wall/CPU stages, RSS and pinned/
  scratch bytes, physical requests/bytes/retries, startup and maintenance.
  Keep logical GETs, SDK attempts and billed requests distinct.
- For semantics-preserving changes require exact results/scorebits and
  declared plan invariants. For quality tradeoffs preserve the full curve;
  don't conceal regressions in a weighted score.
- Define meaningful margins from incumbent variability before inspecting
  candidate measurements. Retain uncertain small gains as candidates rather
  than declaring a win. Full confirmation is required for default promotion.
- Preserve all crashes/INVALID attempts. No partial timed-out run is a valid
  latency result. Repair concrete setup defects, preserving prior receipts.

## Simulation prompting
Ask which retrieval, storage/runtime, statistical and library-user perspectives
would investigate the hypothesis; request their arguments, objections and
falsifiable predictions. These are simulated perspectives, not actual expert
testimony or consensus. Verify consequential claims in code/measurements.
Do not add a panel for trivial changes.

## Records and release
Append results.tsv: attempt, base, candidate, hypothesis, config_sha, split,
outcome, evidence, decision, reason. Outcomes distinguish VALID, INVALID,
RESOURCE_REJECT and pending; missing metrics stay missing.
Maintain incumbent and Pareto candidates. Before Rust integration compile
affected tests, workspace correctness/suspicious Clippy, and actual shim-unset
workspace test-build with bounded jobs. Reuse fresh evidence for unchanged
source. Push coherent verified code/tests/evidence to main by fast-forward.
Production release additionally requires lifecycle/concurrency/recovery and
matched competitor evidence; a codec or query microbenchmark is insufficient.
